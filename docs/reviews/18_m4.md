# Review 18: milestone M4 (parts, sync, place, drawing, route additions)

First review of M4, at commit 32de5fc, binary built from that worktree. Probes are in `tests/review18/`; run them with `python3 tests/review18/check.py target/release/pcb /tmp/review18/run` (set `PCB_R18_BASE` to a project the fixture flow has finished, or the runner runs the flow first; `live18.py` uses the network and runs only when named). At this commit the runner reports 20 passed, 13 failed, 6 notes. Each failure is one of findings 1 to 6.

The fixture flow (`fixture.toml`, all 11 steps) ran to the end on this binary: route in one attempt with 0 nets open and no `plane-split`, check with 0 unwaived findings, release done, drawing done with `labels-omitted` (C14, TP_FISH).

## Findings

1. **FINDING: the pin map reads EasyEDA's spice pin number, not the pin number, so the XC6206 trap passes `pcb sync` in its real form.** `src/easyeda.rs` `pins()` keys each pin by field 3 of the pin's head record (`P~show~0~<spice>~...`). EasyEDA also stores the pin number the symbol shows, in the number segment (`^^1~0~0~0~<number>~...`). For C5446 the two disagree: spice 2 is Vin and spice 3 is Vout, while the numbers say 3 is Vin and 2 is Vout. The Torex datasheet (1 VSS, 2 VOUT, 3 VIN) and the footprint (pad 3 alone on its side) agree with the numbers, so JLCPCB's symbol is right and the tool reads the wrong field. `live18.py` shows lceda.cn serves the same record today. The consequences:
   - A schematic whose XC6206 symbol a converter numbered by the spice field has VBUS on pad 2 (VOUT) and V3V3 on pad 3. It passes sync (`pins18.py` case `spice_numbered_sync`: done, 185 pins checked). This is the swap tscircuit's import made on paddle-keyer.
   - The datasheet-correct schematic is refused (`datasheet_numbered_sync`: `pin-name`). The fixture passes only because `[parts.C5446] pins` restates the datasheet. DESIGN.md, codes.md, `sync.rs` and the fixture's pcb.toml comment all record that JLCPCB's symbol is wrong; that is not so.

   Expected: read the pin number from the number segment, and refuse a component whose spice and displayed numbers name different pads unless pcb.toml gives `pins`. Fix the docs and the fixture comment.

2. **FINDING: pin names that differ only in a sign or an active-low mark compare equal, so a real swap passes.** `canon()` in `src/sync.rs` keeps only ASCII letters and digits and drops active-low marks. D+ and D- both become `D`, IN+ and IN- become `IN`, and Q and ~Q both become `Q`. `pins18.py` gives a part whose symbol has pin 1 named `a` and pin 2 named `b`, then a schematic naming pin 1 `b` and pin 2 `a`. Sync accepts the swap for D+/D-, IN+/IN-, Q/~Q, VREF+/VREF- and CS/CS#. It refuses SDA/SCL, CC1/CC2 and A/K. A USB data pair, an op-amp's inputs or a comparator's outputs reversed on an ordered board would pass. Expected: map `+` to P/POS and `-` to N/NEG inside a name, not only when they stand alone. Keep an active-low mark as part of the name, and allow only spellings of the same mark (`#`, `~`, `/`, `N_`, overbar `~{}`) to match each other.

3. **FINDING: a slot's direction is guessed from the pad's longer side, not read from EasyEDA's hole points.** `easyeda.rs` sets the drill oval along the pad's longer side, or along y when the pad is square or round. EasyEDA records the slot's end points (PAD field 14), which give its real direction. `easyeda18.py` puts two synthetic pads through sync. A round pad with a horizontal slot gets a vertical slot (`round_slot_x`), and a 10 by 8 rectangle whose slot runs along its short side gets the slot turned 90 degrees (`rect_slot_across`). In both, the drill is 90 degrees off what JLCPCB's footprint has, and KiCad DRC sees nothing wrong because the slot still lies inside the pad. The fixture's 48 real parts, J1's four slotted shell pads included, match EasyEDA's outlines, holes and slot directions exactly. Expected: take the slot direction from the hole points, relative to the pad's turn, and refuse a slot that has no hole points.

4. **FINDING: re-sync keeps a part's old LCSC code and value when the new part has the same JLCPCB package.** `sync.rs` replaces a footprint only when its lib id (`jlc:<package>`) changes. Otherwise it only renets the pads, and the LCSC and Value properties stay as they were. `sync18.py` changes R1 in the netlist from 5.1k C25905 to 10k C25744 (both R0402). The second sync reports nothing added, replaced or renetted, and the board still says C25905, 5.1k. `pcb parts` then lists R1 under C25905, and release builds the BOM from the board's LCSC property, so the order would carry 5.1 kΩ. Expected: sync sets LCSC and Value (and any other field it writes) from the netlist on every run, reports the part as changed, and replaces the footprint when the LCSC code changes even if the package name is the same.

5. **FINDING: a two-pad part's rotation is accepted modulo 180 degrees, so a polarised diode or LED can be released reversed.** In `parts.rs` `check()`, `turn_ok` also passes a two-pad part when the solved turn and `rotation_offset_deg` differ by 180. The pads are matched by number, though, so the turn is known exactly (`by_number: true`, residual 0). In `parts18.py` `two_pad_180`, pcb.toml has `rotation_offset_deg = 180` for C2286 (LED1) and C81598 (D1), and `pcb parts` returns done with no finding. `release18.py` carries this through check, gate pass and release: the CPL lists LED1 and D1 at 270 degrees, where v1.0.0 ordered them at 90. JLCPCB would fit both reversed. Expected: when the pads match by number, compare the full turn for every pad count. Allow the modulo-180 case only for a by-shape match, and only for a part the pin map shows is unpolarised. The 0.1 mm offset tolerance for two-pad parts is a note (below).

6. **FINDING: the M4 gate's order drops v1.0.0's pin-in-paste on J1's shell legs, and nothing reports it.** `golden18.py` compares the M4 release's Gerbers with v1.0.0's ordered Gerbers layer by layer, rather than CPL row by CPL row. All 8 v1.0.0 holes match in place and size, and every M4 paste opening holds a v1.0.0 one. v1.0.0 also had paste on J1's four plated shell legs (openings about 1.2 by 1.6 mm at (±4.32, 28.44) and (±4.32, 24.23)), from `[[paste]] pin_in_paste` for J1.13 and J1.14 in the M3 fixture `paddle_keyer_v1/pcb.toml`. The M4 fixture has no such entry, so the M4 board has no paste there. Under Economic assembly (reflow only) the USB-C shell would go unsoldered. `pcb check`'s paste check looks only at SMD pads, and the fixture's oracles compare BOM and CPL rows, so the gate passed. Expected: add the J1 entries to the M4 fixture. Make `pcb check` report a plated through-hole pad of a machine-placed part with no paste and no `hand_fit` or pin-in-paste decision. Extend `verify_release.py` to compare paste and drill against the golden Gerbers.

## Notes

1. **NOTE:** a by-shape match (pad numbers differ) takes the first quarter turn tried when several fit equally, and gives no warning. `parts18.py` `crystal_180`: Y1 renumbered and turned 180 degrees solves to 0 with no finding. The four real-pattern controls (RP2040 QFN at 90 and 180 degrees, USON-8 at 180, SOT-23 at 180) solve correctly, because JLCPCB's patterns are not symmetric. Expected: warn when more than one turn fits within the tolerance.
2. **NOTE:** the CPL offset tolerance for two-pad parts is 0.1 mm, and the pad residual tolerance is 0.15 mm. A 0.09 mm offset error on LED1 passes (`two_pad_offset_009`). That is a fifth of an 0402 pad's width.
3. **NOTE:** the footprint check in `pcb parts` skips bottom-side parts entirely, and release only warns `bottom-cpl-unverified`. The flip itself matches KiCad: `place18.py` places U3, J1, SW1, C2 (at 45 degrees) and Y1 on the back, and every pad position, angle, layer set, drill and silkscreen segment equals pcbnew's own `Flip(TOP_BOTTOM)` followed by the same angle. Text on the back is not mirrored (KiCad mirrors it). That is cosmetic for hidden references and wrong-reading for shown ones.
4. **NOTE:** EasyEDA pads the converter refuses rather than converts. An OVAL pad off a quarter turn, and a pad with copper and an unplated hole (some EasyEDA footprints draw mounting pegs this way), stop sync with code `footprint`, where `parts-cache` would describe the cause better (`easyeda18.py`).
5. **NOTE:** a part with no `componentProductType` in its JLCPCB record passes the Economic check (`product_type` None). Treat a missing field as `missing`.
6. **NOTE:** `[parts.<LCSC>] pins` replaces the whole pin map, so any pin it leaves out goes unchecked without a warning.
7. **NOTE:** place's geometry checks test corners and centres, not overlap. `keepout` looks only at pad corners inside the keep-out rectangle, so a keep-out smaller than a pad and inside it passes. `plated-pad` looks only for the other pad's bounding-box corners or centre inside the part's pads or courtyard, so a strip of body across the middle of a large through-hole pad passes. Neither case is likely with JLCPCB footprints (courtyards are the pads plus 0.1 mm), and the gate's DRC catches copper overlaps.
8. **NOTE:** the DSN's via-to-via clearance comes from the largest via's ring. On a board with two via sizes, the smaller ring's vias can be laid under the hole-to-hole minimum. The gate's DRC (`hole_to_hole`) still catches it. On the fixture the rule is `(clearance 200 (type via_via))`, which is right for 0.6/0.3 mm vias.
9. **NOTE:** `plane-split` and `[[stitch]] join` cannot hide an open. The route gate allows `unconnected_items` and `via_dangling` only for zone nets, and `pcb check` judges DRC absolutely on fresh fills. Join adds vias where its union-find sees separate pieces, and its errors only add vias. Route's `still_open` leaves out zone nets, though, so a GND pad no pour reaches is first reported at check.
10. **NOTE:** the existing M4 tests check less than they claim. `verify_sync.py` D compares pad centres using the same EasyEDA reading as pcb (head origin, 0.254 mm), so it cannot catch findings 1 or 3, pad outlines or holes. `verify_release.py`'s CPL match is circular, because `[[place]]` was copied from v1.0.0's CPL. `m4_cases.py`'s XC6206 case asserts the refusal that finding 1 shows is the wrong behaviour.

## Gate verdict

The fixture flow runs from schematic to release and drawing with `pcb` commands only, and no per-board code. Per-board data (places, waivers, the C5446 pin override) sits in pcb.toml, which is what the gate allows. The claim "paddle-keyer from netlist to order" is not yet true as an equivalence to v1.0.0's order, for two reasons:
- The released board has no pin-in-paste on J1's shell (finding 6).
- The pin check passes because of a pcb.toml override that hides the tool reading the wrong pin field (finding 1).

The oracles cannot detect either, since they compare BOM and CPL rows copied from v1.0.0. Findings 2, 4 and 5 let a wrong connection, part or rotation reach an ordered board on other designs. Close all six before M4 passes.
